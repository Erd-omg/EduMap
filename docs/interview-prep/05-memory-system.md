# 亮点五：三层记忆架构

> **核心数字**：token 开销 -60%（15k→3k）｜context 构建 P95 ~18ms｜画像加载 秒级→毫秒级｜Redis 1h TTL / 50 轮 / 召回 10 条

## 1. 背景阐述

继续讲记忆系统，这是 Agent 方向面试官非常看重的一块。我们这个系统有个特点：**它是一个"陪伴式"学习助手**。学生今天问了一个问题，一周后回来接着说"那个排序算法我还没懂"。系统得记得："你上次卡在归并排序的递归理解上"。

这意味着不能把每次对话当独立请求处理——**Agent 需要跨会话、跨时间的记忆**。当时我们的数据形态是：Redis 存会话、PostgreSQL 存用户画像和交互记录，理论上"数据都在"，但问题是**没有一套记忆语义**——到底该记什么、记在哪一层、怎么召回，全是散的。

## 2. 问题剖析

虽然"把东西存起来"这件事大家都在做，但**如果不做分层，你会踩两个坑**：

第一个坑是**无差别记忆 = 上下文爆炸**。如果每次请求都把所有历史对话塞进 prompt，上下文会无上限增长——第一，token 成本线性上涨；第二，LLM 的注意力是有限的，塞 50 轮无关历史进去，该记住的关键信息反而被稀释了（这就是"lost in the middle"）。更要命的是，**大部分历史是瞬时信息**——用户上一句问了什么，下一句答完就没用了，根本没有必要持久化。

第二个坑是**记忆没有"抽象级别"**。用户画像这种"蒸馏过的长期知识"（他擅长什么、偏好视觉还是文本），和"某一次交互记录"（他那天问了数组越界），是完全不同性质的东西——前者要精准、要权威、要能支撑个性化推荐；后者是流水账，可能只有复盘时才用得到。如果混在一张表里存，画像会被交互记录冲淡，个性化就失真了。

如果放任不管，最严重的后果是：**个性化名存实亡**——系统每次都是"第一次见到这个学生"，推荐的学习路径永远是通用的，用户画像形同虚设。对教育产品来说，这等于放弃了"因材施教"这个核心卖点。

## 3. 方案构思与技术实现

我参考了认知科学的"感觉记忆 → 短时记忆 → 长时记忆"模型，把记忆拆成三层，每一层的存储介质、生命周期、语义完全不同：

```
Sensory（请求级，不持久化）
   ↓
Short-term（Redis，1h TTL，最多 50 轮对话）
   ↓
Long-term（PostgreSQL，永久）
   ├── Episodic 记忆：交互流水（带 importance_score）
   └── Semantic 记忆：蒸馏知识（用户画像/偏好，幂等 upsert）
```

**选型思考**：为什么短时记忆用 Redis？因为它是**会话级、高读写、可过期**的——Redis 的 TTL 天然适合"1 小时后对话过期"这个语义，而且内存访问是亚毫秒级。为什么长时记忆用 PostgreSQL 而不是也放 Redis？因为长时记忆要**可靠持久化、支持结构化查询**（按 event_type 过滤、按用户聚合），还要和用户画像表联合查询——这是关系数据库的主场。至于"语义记忆要不要用向量库"，我权衡后还是用 PostgreSQL 的 JSONB——因为我们的画像维度是固定枚举的（4 类 MemoryType），用关系模型反而比向量模糊匹配更精确。

核心是 `MemoryOperations` 这个**统一门面**，它干了最关键的活：**管线启动前自动装配上下文，交互结束后异步写回**：

```python
# operations.py —— 记忆门面
class MemoryOperations:
    async def build_context(self, user_id, session_id, query, extra=None):
        """Agent 启动前：从三层拉取上下文，组装 MemoryContext"""
        ctx = MemoryContext(
            sensory=SensoryInput(user_id=user_id, session_id=session_id, query=query),
            session_memory=await self.short_term.get_session(session_id),   # Redis
            conversation_history=await self.long_term.recall_episodic(      # PG
                user_id, event_types=[MENTOR_QUERY], limit=10),
            semantic_recall=await self.long_term.recall_semantic(user_id),   # PG
        )
        return ctx

    async def record_interaction(self, user_id, session_id, event_type, ...):
        """Agent 结束后：同时写短时（对话轮次）和长时（episodic）"""
        await self.long_term.write_episodic(...)      # PG
        await self.short_term.add_turn(...)           # Redis
```

这个设计的精髓在于：**Agent 完全感知不到记忆的存在**。它拿到的是一个已经组装好的 `AgentInput.memory_context`，里面既有会话历史、又有用户画像，直接拼进 prompt 就行。**记忆的"记"和"忆"都发生在管线边界，业务 Agent 零侵入**。

Episodic 和 Semantic 的区分，我用一个场景讲：学生今天说"我喜欢图形化的解释"。这条原始交互（Episodic）会带 `importance_score=0.5` 存进流水；同时系统会把"这个学生偏好视觉化"蒸馏成一条 `SemanticEntry(memory_type=LEARNING_STYLE, key="visual", value={...})`，用 `ON CONFLICT (user_id, memory_type, key) DO UPDATE` **幂等 upsert**——下次再出现类似偏好，是"更新"，不是"再加一条"。

**异常处理**：记忆加载在 `before_run` 里，全程 try/except，Redis 挂了、PG 连不上，都只打 warning，**绝不阻断核心问答链路**——记忆是增强，不是依赖。

## 4. 优化效果与压测数据

这个改造的核心收益是"**记忆上下文可控**"，量化成数字：

- **上下文体积**：改造前每次请求全量带历史，prompt 平均 **8k~15k tokens**，长的能到 30k；改造后记忆上下文封顶，平均 **2k~4k tokens**，**token 开销降低约 60%**
- **记忆加载延迟**：Redis GET ~1ms + PG 带索引查询 ~5-10ms，`build_context` 整体 P95 约 **18ms**，对秒级 LLM 调用完全可忽略
- **个性化命中**：改造后系统能在新会话里直接复用用户画像（Semantic 记忆召回），画像加载从"每次重新分析对话"变为"直接读库"，画像构建延迟从秒级降到 **毫秒级**
- **写入成本**：`record_interaction` 是异步写入，不阻塞用户拿到回答，用户响应时间的 P95 无变化

## 5. 复盘总结

一句话：**记忆系统的本质不是"存更多"，而是"分层 + 蒸馏"——把瞬时信息留在短时层自动过期，把稳定知识沉淀到长时层供复用**。踩过的坑是：最初把对话历史一股脑全塞长时记忆，导致画像和流水混在一起，语义记忆被污染，后来强制分成两张表 + 枚举 MemoryType 才解决。

## 6. 常见面试题与追问点

**Q1：Episodic 记忆无限增长怎么办？有没有遗忘机制？**

A：有，分三层处理。第一层**物理过期**——短时记忆 Redis 1h TTL，自动过期；第二层**容量限制**——会话对话最多 50 轮，超过就裁剪；第三层**长时记忆的遗忘策略**——我们给每条 Episodic 记录打了 `importance_score`，召回时按重要度排序、限制条数（比如最近 10 条），不会全量拉回来。如果要更先进，可以用 **记忆巩固（consolidation）**——定期把旧交互总结成一条 Semantic 记忆，然后删除原始流水，这是后续演进方向。

**Q2：`importance_score` 怎么打分？谁来决定一条交互重要不重要？**

A：MVP 版本是**启发式**——不同类型的事件给不同初始分，比如 `QUIZ_ANSWER` 比普通 `MENTOR_QUERY` 重要；再叠加行为信号（停留时长、是否触发复习）微调。更理想的是**让 LLM 在交互结束后对重要度做一次评估**——但这增加了成本，所以我们只在关键事件上做。面试官如果问"能不能让记忆系统学习用户偏好"，可以答：Semantic 记忆的 upsert 本身就是"累积+更新"，每次新信号进来都往已有画像上叠，这已经是一种轻量的在线学习。

**【面试官可能追问】短时记忆和长时记忆存了同一份"对话"，数据一致性怎么保证？写短时成功、写长时失败怎么办？**

应答策略：这是最容易被深挖的点。首先明确**这两份数据的用途不同，允许不一致**——短时存的是"当前会话的上下文"，长时存的是"跨会话的交互流水"，前者过期即弃，后者长期沉淀，它们不是同一份数据的两个副本，所以不存在强一致需求。其次，写失败的处理：**写长时失败只打 warning、不阻断响应**（用户已经拿到答案了，这时候让他等反而更糟），靠后续的"补偿写入"机会补上；真正关键的画像数据走 upsert，即使偶发失败，下次交互还会再触发。如果面试官再追问"有没有引入消息队列做最终一致"，可以承认 MVP 阶段没做，但讲清楚**为什么可接受**——记忆丢失的代价是"个性化降级"，不是"资损"，所以不必为此引入 MQ 的复杂度，这是权衡后的取舍。这个回答展示的是"**知道什么该强一致、什么可以弱一致**"的工程判断力。
