# 亮点四：RAG 评测与优化闭环

> **核心数字**：MRR 0.841｜HitRate@3 0.930｜P@1 0.755（+12% vs baseline）｜Faithfulness 0.620｜Answer Relevancy 0.716｜20 条标注集一轮评测 ~2min

## 1. 背景阐述

这个亮点和上一个是连续的。RAG 系统改完第一版之后，我面临一个很尴尬的局面：**我改了一版检索逻辑，但我没法证明它变好了**。当时团队内部对检索质量的评价方式，是人工把几条查询跑一遍，肉眼看返回结果"像不像"——这完全不可靠，换个数据、换个查询，结论就变。

所以我当时的目标很明确：**给 RAG 装上"仪表盘"，把检索质量和生成质量全部变成可量化的数字**。

## 2. 问题剖析

虽然大家都知道"要评测"，但**RAG 评测难在哪？** 难点有三层：

第一，**评测标准不统一**。检索质量看什么？光看召回准不准不够，还要看排序好不好、第一名准不准、前 K 名有没有命中——这分别是 Precision、MRR、HitRate、NDCG 这些不同的维度，没有一个能包打天下。

第二，**生成质量更难量化**。检索对了，不代表 LLM 答得对。生成的东西有没有"忠实于上下文"（faithfulness）？有没有"切题"（relevancy）？这俩没有一个客观的 ground truth 可以比。你没法给一句话标一个"标准答案"然后算对错。

第三，**评测成本高**。如果要人工标注，20 条查询 × 人工判读返回结果，每次改版都要来一遍，一次几小时，根本做不了"快速迭代"。

如果放任不管，最直接的后果就是：**优化靠感觉、回退靠运气**——你可能这次改坏了检索，但没人发现，直到线上用户反馈"回答变差了"才后知后觉，而那时候你已经不知道是哪次改动引入的。

## 3. 方案构思与技术实现

我的方案是搭一个**两层评测框架**：底层是 9 个 metric 函数，上层是一个 `RAGEvaluator` 编排管道，分"检索侧评测"和"生成侧评测"两条腿。

**检索侧**用的是标准信息检索指标，全部从零实现：

```python
# metrics.py —— 检索质量指标
precision_at_k(retrieved, relevant, k)   # 前 K 中相关占比
recall_at_k(retrieved, relevant, k)      # 召回了多少相关
mean_reciprocal_rank(retrieved, relevant) # 第一个相关结果的排位倒数
ndcg_at_k(retrieved, relevant, k)         # 考虑排序位置的信息增益
hit_rate_at_k(retrieved, relevant, k)     # 前 K 是否至少命中一个
```

**生成侧**就涉及技术选型的纠结了。当时有两条路：**词重叠启发式**和 **LLM-as-Judge**。

- 词重叠启发式：计算答案句子和上下文的重叠率，阈值 0.3 判断"这一句有没有依据"。优点：快、免费、稳定；缺点：**不智能**，"改个说法、换个同义词"就判不出来。
- LLM-as-Judge：用另一个 LLM 当裁判，逐句分析答案是否被上下文支撑，输出结构化评分。优点：准，能理解语义；缺点：**贵、慢、而且裁判本身可能有偏见**。

我最后的决策是**双模式并存**：默认跑启发式（便宜，CI 里每次都能跑），需要精确评估时跑 LLM-as-Judge（比如发布前的重点回归）。并且 LLM-judge 失败时**自动回退**到启发式，保证评测管道永远有输出。这是很典型的"**快路径保底 + 慢路径保准**"设计。

核心的 `EvalResult` 还做了一个很有意思的事——把 6 个指标**加权合成一个总分**：

```python
@property
def overall_score(self) -> float:
    return round(
        0.25 * avg_precision + 0.25 * avg_recall
        + 0.15 * self.mrr + 0.15 * avg_ndcg
        + 0.10 * self.faithfulness_score + 0.10 * self.relevancy_score, 4)
```

**为什么权重这么定？** 检索类指标加起来 0.8、生成类占 0.2，是因为我们的核心瓶颈在检索侧，生成侧 LLM 已经很强，拉不开差距。这个权重不是拍脑袋，是观察指标"变动灵敏度"后调的——选那些"改了检索就能明显变化"的指标当主干。

**评测数据从哪来？** 两条数据源：一是**手工标注**的 20 条学生问答数据集（数据结构与算法领域，每条标注了 relevant 文档 id 和标准答案），这是黄金标准；二是**从知识图谱自动生成**——用知识点名当查询，用图谱的 prerequisite/related 关系当 ground truth，可以低成本扩充评测集。后者有个前提，就是评测的时候要明确标注数据来源，别把自动生成的当人工标注用。

## 4. 优化效果与压测数据

第一版评测跑出来的 baseline，就逼出了三个我们之前没意识到的优化点：

- **初始状态**（纯 bi-encoder + 固定分块）：MRR ≈ **0.72**，HitRate@3 ≈ **0.83**
- **加了语义分块之后**：HitRate@3 升到约 **0.86**，说明分块质量确实影响召回
- **加上 Cross-Encoder 精排之后**（这是最优配置）：
  - **MRR = 0.841**，**HitRate@3 = 0.930**，**P@1 = 0.755**
  - 相比 baseline，MRR 提升约 **17%**，HitRate@3 提升约 **12%**
  - P95 检索延迟增量控制在 **150ms 内**
- **生成侧**：Answer Relevancy = **0.716**，Faithfulness = **0.620**

对 Faithfulness 只有 0.62 这个数，我多说一句——这正是评测框架的价值：它暴露了"生成侧忠实度偏低"这个之前根本看不见的问题。根因是上下文里混入了部分低相关片段（top-20 粗筛的噪声），精排虽然把它们排到后面了，但 LLM 还是会读到。我们后续的对策是**严格收紧上下文预算**（从 2000 字符压到更小，只留高相关片段）和**强制引用格式**，再跑评测看数字是否回升。

**评测跑一轮的成本**：20 条查询 + 检索评测，纯本地模型，一轮大约 **2 分钟**；加上 LLM-judge 生成评测，限制 3 条，约 **1 分钟**。这意味着**每次改检索逻辑都能在一杯咖啡的时间里拿到回归结论**，这才是"闭环"的底气。

## 5. 复盘总结

一句话：**评测不是加分项，是 RAG 工程的底线**——没有评测框架，之前所有的检索优化都是"玄学优化"。最大的教训是：**指标之间的优先级要想清楚**，我们一度沉迷把 MRR 刷高，结果发现 MRR 高但 P@1 低的组合，意味着"第二名才对"——对用户体验来说不如 P@1 稳定，后来我们就把 P@1/HitRate 作为主目标，MRR/NDCG 作为参考。

## 6. 常见面试题与追问点

**Q1：LLM-as-Judge 本身有偏见怎么办？怎么校验 judge 的可靠性？**

A：对，这是个经典问题，LLM 裁判可能偏爱更长更华丽的答案（**长度偏置**）、偏爱自己的风格（**自利偏置**）。我们的做法：一是**prompt 里强约束**——要求逐句分析、给出理由，不接受笼统评分；二是**双模式交叉验证**——LLM-judge 结果和词重叠启发式结果做相关性分析，如果两条腿差太多，说明数据集或 prompt 有问题；三是**保持 judge 模型固定**——评测基线一旦用某个模型，就锁定它，避免换模型导致分数漂移。如果要做严谨的实验室评测，会进一步和人工标注做一致性分析（Cohen's Kappa）。

**Q2：20 条标注数据够吗？样本量这么小，指标波动会不会很大？**

A：够用于**开发期的回归门禁**，但不足以做严谨结论。20 条是我们的"冒烟集"——每次改版先跑它，通过才放行。真正的置信结论我们靠**图谱自动生成的大评测集**（几百条），它在量上补足了标注集的不足，但牺牲了标注质量。所以策略是：**小标注集保证"质"，大自动集保证"量"，两套并行**。如果面试官问 CI 里跑哪套，答：CI 里跑小标注集（快、稳定），大自动集在发布前手动触发。

**【面试官可能追问】Faithfulness=0.62 这个数很低，你会怎么提升它？**

应答策略：面试官如果盯着这个数，说明他很懂行。应答分三层：(1) **承认问题**——0.62 确实不达标，我们目标 0.8+；(2) **根因分析**——不是 LLM 的问题，是**上下文污染**：top-20 粗筛的噪声片段混进了上下文，LLM 忠实引用了它，忠实度就低了；(3) **对策**——a) 收紧上下文预算，只保留 cross-encoder 排在前 3 的片段；b) 生成 prompt 里强约束"只基于引用来源作答，无依据就明说不知道"；c) 用 citation accuracy 指标反过来约束格式，强制带 `[N]` 引用。最后补一句"我下一次改版就是用评测框架验证这三条措施各自贡献了多少提升"。这个回答展示的是"**用评测驱动优化**"的完整闭环，比直接说"我调了 prompt"高级得多。
